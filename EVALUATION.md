# Evaluation

**Question:** does an LLM understand an unfamiliar relational database measurably better when it has structural evidence (B),
and then outcome-driven predictive evidence (C), than when it sees only the schema (A)?

The full pre-registered protocol is in [`eval/protocol.md`](eval/protocol.md). It and the ground-truth key
([`eval/ground_truth/avito.json`](eval/ground_truth/avito.json)) were committed to git before any discovery, prediction or
LLM output existed. The git history is the evidence for that ordering.

## Method in brief

- **Dataset:** RelBench `rel-avito` (an online classifieds marketplace).
  - 8 tables, about 25M rows.
  - Outcome: the RelBench `user-visits` task. Does a user visit more than one ad in the 4 days after a cutoff?
  - Splits are RelBench's time-based splits.
- **Development dataset:** RelBench `rel-f1`. Heuristics were tuned only here.
- **Ground truth for relationships:** RelBench's published foreign-key metadata (11 edges). This is independent of this project.
- **Ground truth for semantics:** reconstructed from the Avito competition's data description. It is **provisional until a human verifies it.**
- **Conditions:** a 3 × 2 design, three configurations by two naming conditions, with 3 runs per cell.
  - The **masked** condition renames every table to `T01..T08` and every column to `c01..`, and hides free-text values.
  - It is the primary test. The model has very likely seen these public datasets, so with real names it could "understand" them from memory.
- **Scoring:**
  - Relationships are scored by exact match.
  - Entity and column meanings are scored by a blinded LLM judge on a 0/1/2 rubric. The judge never sees the configuration or the naming condition.
  - Unsupported claims are counted three ways: citations to evidence that doesn't exist, confident answers (≥ 0.8) that are wrong, and causal wording.

## Results so far

All numbers come from `results/avito/` and are regenerated by `python -m sde report`.

### Structural component alone (deterministic, no LLM)

| Edge set | Precision | Recall | F1 | Edges proposed |
|---|---|---|---|---|
| All candidates passing 95% value inclusion | 0.096 | 1.000 | 0.175 | 115 |
| Preferred parent per column | 0.379 | 1.000 | 0.550 | 29 |
| Feature-eligible (preferred, non-weak, enough distinct values) | 0.556 | 0.909 | 0.690 | 18 |
| Primary keys | 1.000 | 1.000 | 1.000 | 5 |

On the development dataset (`rel-f1`), the same rules gave precision/recall of 0.05/1.00, then 0.43/1.00, then 0.60/0.92. The Avito figures
are in the same range, which suggests the rules were not overfit to the development set. But two datasets are very little evidence.

**What this shows.**
- **Value overlap is almost no evidence on this data.** RelBench renumbers every key to a dense range `0..N-1`. So almost any integer column
  with values below N "fits" almost any key. Every candidate on Avito has `range_density = 1.0`.
- **Choosing the best parent recovers all 11 true edges** in a list of 29. But the false ones are not random noise. They include
  - anonymized IP-address IDs matched against search IDs;
  - city IDs matched against user IDs;
  - browser and device codes matched against user IDs.
  
  Data alone cannot separate these from real links. That is the specific job configurations B and C give the LLM.
- One true edge (`SearchInfo.CategoryID -> Category`) is flagged "weak", because both sides are small integer ranges. So the feature step never uses it.

### Outcome-driven component alone (held-out test split)

| Model | Validation AUROC | Test AUROC |
|---|---|---|
| Gradient boosting (72 relational features) | 0.703 | 0.671 |
| Logistic regression (72 features; selected on validation) | 0.704 | 0.668 |
| Baseline: best single past-activity count (`count(VisitStream)`) | 0.683 | 0.655 |
| Baseline: base rate | 0.500 | 0.500 |

**Data and procedure**
- Label rows: 86,619 train, 29,979 validation, 36,129 test. Positive rate: 0.91, 0.90 and 0.85.
- Recomputing "more than one visit event in [t, t+4d)" agrees with the supplied label on 98.4% of rows. We are therefore modeling the outcome its definition describes.
  The 1.6% gap is unexplained (perhaps RelBench counts distinct ads). This check is for validation only and is never shown to the LLM.
- Features walk the inferred relationships up to 2 hops, using only rows dated before each cutoff. Unit tests confirm that rows at or after the cutoff change no feature value.

**What this shows**
1. **The relational features add little on top of one strong count:** +0.013 to +0.016 test AUROC. The outcome is dominated by "how active was this user recently".
2. **Ranking which paths matter works as intended.** Permutation importance concentrates on the path from users to visit events (0.33). Phone-number requests (0.03) and searches (0.01) follow.
   - In masked form, this tells the LLM *which unnamed table the outcome is about* without naming it. Whether that helps interpretation is what H2 tests.
3. **Statistical significance did not protect against invalid joins.** 26 of 72 features pass Benjamini–Hochberg at q < 0.05. Among them are two built on the false
   `IPID -> SearchInfo.SearchID` join (`f031`, `f037`).
   - They have stable direction across cutoffs and validation AUROC of 0.55–0.57.
   - They work because more activity means more chance matches against random IDs. The signal is real, but it does not reflect what the join means.
   - Implication: **predictive evidence must not be used to confirm relationships.** Only structural or human evidence can do that.

**Pre-registered hypotheses.** All of them come out "no detectable difference", under both naming conditions:
- **H1** (B beats A on relationships): no detectable difference.
- **H2** (C beats B on semantics): no detectable difference.
- **H3** (C adds no overconfident errors): there were none in any cell.

**The result is a ceiling effect, not evidence against the hypothesis.** Schema-only config A already scores at or near the maximum. With
masked names it recovers 11/11 relationships with no false positives and identifies all 8 tables correctly. This leaves no room for B or C to show an improvement.

#### Why A scores so high: probable recognition of the dataset

With every table and column name masked, the model never names the dataset. But its answers follow the original Avito competition
documentation too closely for blind inference. For example, it described a masked small-integer column as an ad type of
"regular, highlighted, context", which is almost word for word the documented values of `ObjectType`. The masked packet still carries fingerprints:
- Cyrillic ad titles (described, not shown);
- the exact 2015 date range;
- distinctive row counts and table shapes;
- ID values shared across tables, which the model used to pair columns.

**Conclusion:** name masking does not prevent recognition of a well-known public dataset. The pre-registered design therefore **cannot
answer the central question on `rel-avito`.** This is the most important finding of this run. It is the kind of contamination that makes
LLM-on-public-data demos look better than they are.

#### What the errors were

| Error | Where | Assessment |
|---|---|---|
| `Category.ParentCategoryID -> Category` proposed as a relationship (the only "false positive" with original names; 1 of 3 masked runs in C) | A/B/C original (every run); C masked (1 run) | This was the pre-registered **adjudication candidate**: a plausible self-reference that RelBench's metadata omits. Treated as correct, relationship precision is about 1.0 in every cell. |
| `Category.SubcategoryID -> Category` | B masked, 1 run | Plausible but unverifiable; the column is undocumented. |
| `SearchStream` labeled "bridge" instead of "event" | 5 of 6 B runs, 2 of 6 C runs, 0 of 6 A runs | Defensible: it is an impression table that links searches to ads. Notably this appears **only once structural evidence is added**, so the evidence changes how the model frames the table, not whether it understands it. |
| `UserInfo.UserAgentOSID / UserAgentFamilyID / UserDeviceID` swapped or vague | Masked runs | Four anonymous integer codes. Neither values nor structure can tell them apart. No configuration solved this, and none should be expected to. |
| One outcome statement judged causal | C masked, run 1 | "...which would explain why past view volume is the dominant predictor (behavioural persistence)". Borderline: an explanatory hypothesis rather than a claim that an intervention would work. |

#### Secondary observations (not pre-registered as primary; treat as exploratory)

- **Calibration of human-review flags.** With masked names, adding evidence reduced the items the model flagged for human review from about 40 (A)
  to about 31–32 (B, C), with the same accuracy. That gap is larger than the run-to-run range. With real names the flags went *up* (7 → 13).
  So evidence may help the model judge *what it actually knows*. But with accuracy at the ceiling, this cannot be separated from noise in how the model hedges.
- **Cost:** B costs about 1.4× A and C about 1.6× A, mostly from 5–8× more input tokens, with no measured accuracy benefit on this dataset.
- **The judge gave full marks to every original-name answer.** That could mean the answers were all correct, or that the judge is lenient. The pending human audit
  (`results/avito/judge_audit/`) is needed before trusting the semantic scores.

## Experiment 2: synthetic SaaS warehouse (`saas`)

**Why.** Experiment 1 could not discriminate, because the model recognized `rel-avito`. Experiment 2 uses a warehouse generated fresh for a
fictional company (`sde/synth.py`, seed 20261027). Its ground truth is *true by construction*. The design was pre-registered in protocol
amendment 2, and the answer key and evidence packets were committed before any LLM run.

**Data**
- 9 tables with legacy-style names (`ACCT_MSTR`, `EVT_STRM_01`, …) and sparse random entity keys.
- 20,000 trial accounts, about 85k users, 13.6M usage events, 4.2k subscriptions.
- Outcome: trial-to-paid conversion. Labels are evaluated at trial day 5; 18.5% positive.
- Planted in the data:
  - positive signals: usage codes 7 and 4, overall usage, email opens;
  - negative signals: usage code 11, severity-1 tickets;
  - a null signal: the number of scheduled emails.
- A leakage trap: usage surges after conversion.

### Deterministic components

| Structural edge set | Precision | Recall | Edges |
|---|---|---|---|
| All candidates | 0.30 | 1.00 | 33 |
| Preferred parent | 0.43 | 0.90 | 21 |
| Feature-eligible | **1.00** | 0.70 | 7 |

- **Structural misses match the prediction recorded in the protocol:** two joins to dense lookup tables (flagged "weak") and the optional 1:1 `SUB_HDR.acct_key` link, which the key-to-key rule rejects.
- **Outcome model:** test AUROC 0.746 (logistic regression; gradient boosting 0.740). The best single activity count scores 0.570.
  - The label check matches 100%.
  - The leakage trap was not triggered. Using future rows would give about 0.99.
  - All 6 planted signals appear in the outcome evidence with the correct direction. The null signal shows AUROC 0.500 and q = 1.

**Pre-registered hypotheses (masked names, primary)**

| Hypothesis | Result |
|---|---|
| H1: B beats A on relationship F1 | **No detectable difference.** The mean rose from 0.835 to 0.968, but A's run-to-run range (0.71–1.0) is wider than the gap. |

| H3: C adds no overconfident errors | Confirmed: there were none in any cell. |

**Exploratory comparisons, A vs B (masked).** These were not pre-registered as hypotheses. Same decision rule:
- **Column semantics improve:** all columns 0.678 → 0.944; recoverable columns 0.732 → 0.985. Both gaps are larger than the run-to-run range.
- **Items flagged for human review drop** from 46 to 35.
- Entity concepts rise from 0.76 to 1.00. That gap is still within A's large run-to-run range.

### What Experiment 2 shows

1. **With no prior knowledge to lean on, structural evidence is what turns guesses into understanding.**
   - With masked names, schema-only A got about two-thirds of column meanings right and was erratic: one run misread the ticket table and the user table.
   - Adding deterministic structure (B) brought recoverable-column accuracy to 98.5%, identical across runs. It also made the model *less* uncertain where it had reason to be.
   - This is the clearest evidence so far for part of the hypothesis. It is exploratory, though, because the pre-registered H1 measured relationships rather than column meaning.
2. **Outcome evidence (C) adds discovery, not understanding.**
   - C found 94% of the planted business signals with no wrong-direction or spurious claims. B and A cannot do this at all.
   - C did *not* improve semantic interpretation over B. The planted signals live in code values (event code 7, severity 1) whose business meaning no data can reveal.
   - **So C can tell you "event code 4 precedes conversion; find out what code 4 is", but not "code 4 is connecting an integration".** That is the distinction the project brief asked us to keep explicit.
3. **More evidence carried a reliability cost.**
   - One of the three C/masked runs (r3) left an entire table (5 columns) out of its output despite the instruction to cover every column. That single run drives C's lower average.
   - The same run also misread the users table as a hierarchy of objects. The cause appears to be the self-referencing `inv_by` column, not the outcome evidence.
   - This is one run in three, so it is weak evidence. But it is a real risk for larger databases: bigger evidence packets may need chunking or a completeness check.
4. **Even cryptic legacy names gave the model almost everything.** With original names, every configuration scored 1.0 on every semantic metric.
   - Names like `TKT_LOG.sev` and `SUB_HDR.end_ts` were enough. The judge may also be somewhat lenient; the human audit is pending.
   - In practice, names, however abbreviated, are the strongest single source of meaning. Structural and outcome evidence matter most when names are missing or misleading.

## Threats to validity (and what is done about each)

| Threat | Status |
|---|---|
| **Memorization**: Avito/RelBench are public | The masked condition is primary. Original names are reported as secondary, to *measure* how much names and memory contribute. |
| **The developer knew the schema** | Structural rules use no names; thresholds were fixed in the protocol and tuned on `rel-f1`. Disclosed in the protocol. |
| **Semantic key written by the developer** | Avito: marked provisional; a human should verify it. Synthetic: true by construction. |
| **Synthetic data is simpler than real data** | One generator, one domain, clean values. The developer knew the planted structure, though the LLM never saw it. Results show what the method can do when signals exist; they are not real-world accuracy. |
| **LLM judge bias** | The judge is blinded to configuration and naming. Every decision is saved to `judge_audit/`. A human audits 30 decisions and the agreement rate is reported. |
| **Small sample**: 8 tables, 11 edges, 42 columns, 3 runs | The decision rule requires the gap to exceed run-to-run range. Results describe this dataset only. |
| **One dataset, one domain** | Not addressed in V1. This is the main limit on generalization (see next steps). |
| **Leakage** | Point-in-time filtering, unit-tested. Static tables (users, ads, locations) have no timestamps and could contain later information. |
| **Invalid joins in features** | Present and documented (see above). Features from spurious edges are kept, not hidden, because a real system would face the same noise. |
| **Multiple testing** | Benjamini–Hochberg on 72 univariate tests, plus a stability check across 3 training cutoffs. |
| **Causal language** | Prohibited in the prompt and counted as an unsupported claim (keyword check plus judge). |

## Lessons learned so far

- **Structure helps understanding; outcomes help discovery.** On data the model could not have seen, structural evidence raised masked column accuracy from 0.68 to 0.94.
  Outcome evidence surfaced the planted business signals reliably, but did not improve interpretation further.
- **The extra evidence does not cause hallucinated certainty.** Across 36 synthetic and 36 Avito calls: zero invalid citations, zero overconfident errors, and
  (synthetic) zero claims about the null signal.

0. **A public benchmark can be useless for testing semantic discovery, even with names masked.** The model's prior knowledge of the
   dataset saturated the easiest baseline. The next experiment needs data the model cannot have seen, or much deeper anonymization.

1. **Dense surrogate keys make value-based foreign-key discovery mostly guesswork.** Real warehouses have the same problem (auto-increment IDs).
   The structural component's honest output is a ranked list of candidates, not an answer. This makes the LLM's resolution step the critical one.
2. **Predictive signal is a good pointer but a bad validator.** It correctly points at the table the outcome is defined on. It also makes a false join look significant.
3. **The benchmark's preprocessing shapes what can be discovered.** RelBench renumbered keys and dropped two dictionary columns. Results on raw
   warehouse data could differ in either direction.
